# Contributing to SubParser

Спасибо за интерес к проекту. Ниже — краткое описание веток, релизного процесса и проверок перед PR.

## Ветки

| Ветка | Назначение |
| :--- | :--- |
| **`main`** | Стабильная ветка. Сюда попадает только проверенный код. Пуш тега `v*` запускает сборку и публикацию GitHub Release. |
| **`beta`** | Новые функции и исправления. Каждый пуш собирает IPK/APK/архив как artifacts GitHub Actions, но не публикует релиз. |
| **`old`** | Архив предыдущей реализации ядра **v2.1.9**. Новые функции сюда не переносятся. |
| **`fix/...`, `feat/...`** | Временные ветки от `beta`. Вливаются в `beta` через pull request. |

## Порядок работы

1. Создайте отдельную ветку от `beta`.
2. Внесите изменения и проверьте их локально.
3. Откройте pull request в `beta`.
4. После проверки изменения вливаются в `beta`; CI собирает тестовые пакеты.
5. Проверенная версия вливается из `beta` в `main`.
6. Перед релизом поднимите версию пакета в `root/etc/subparser_pkg_version`.
7. Поставьте на `main` тег `vX.Y.Z` и запушьте его — запустится публикация релиза.

Прямые коммиты в `main` рекомендуется запретить через branch protection в настройках GitHub.

## Версии

- Версия ядра парсера хранится в `root/etc/subparser_version`.
- Версия пакета и релиза хранится в `root/etc/subparser_pkg_version`.
- Тестовые beta-пакеты получают версию вида `1.0.0-r<номер_запуска>` через `PKG_RELEASE=${GITHUB_RUN_NUMBER}`.
- После установки beta-пакета переход на стабильную версию с меньшим номером может потребовать переустановки. Для стабильного обновления используйте следующий релиз с более высокой версией.

## Проверки перед PR

```sh
python3 -m unittest discover -s tests -v
python3 -m py_compile root/usr/bin/subparser.py root/usr/bin/subparser-bot.py \
  root/usr/lib/subparser/*.py
node --check root/www/luci-static/resources/view/subparser.js
```

Для shell-скриптов:

```sh
for f in *.sh; do sh -n "$f"; done
```

## Локальная сборка релиза

```sh
sh build-release.sh
```

Скрипт создаст в `dist/` IPK, APK, `subparser-1.0.0.tar.gz` и `SHA256SUMS`.
Для APK нужен `apk-tools` 3; если его нет, `build_apk.sh` автоматически использует Docker-образ `alpine:edge`.

## Стиль изменений

- Не смешивайте в одном PR несвязанные исправления.
- Сохраняйте существующую структуру и стиль кода.
- Для новых функций добавляйте или обновляйте тесты в `tests/`.
- Обновляйте README только там, где меняется поведение для пользователя.
